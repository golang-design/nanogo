# ABI

Every rule here is `gc`'s rule, by [000](000-decisions.md) decision 10. Nothing
in this spec is a design; it is a transcription with the consequences drawn out.
A deviation is not a different choice, it is a bug that corrupts memory.

Type layout is `ir.Layout`. The calling convention is the assignment walk in
`ssa/abi.go` and the pass that rewrites a function to realise it. Both are
built. Over 536 packages of the distribution the assignment **walk** refused 0
of the 20,850 functions that reach SSA construction, and it still does: what
the **pass** refuses is a call-site result it cannot place, which is 6 of the
3,076 functions of the sampled corpus and is the bound the section below names.
ABI0 recording is the one part of this spec with no code, and the section below
says what it would take.

## Type layout

Sizes and alignments follow the specification and the reference implementation:

| Type | Size | Alignment |
| --- | --- | --- |
| `bool`, `int8`, `uint8` | 1 | 1 |
| `int16`, `uint16` | 2 | 2 |
| `int32`, `uint32`, `float32`, `rune` | 4 | 4 |
| `int64`, `uint64`, `float64`, `int`, `uint`, `uintptr`, pointer | 8 | 8 |
| `complex64` | 8 | 4 |
| `complex128` | 16 | 8 |
| `string` | 16 | 8 |
| slice | 24 | 8 |
| interface, `any` | 16 | 8 |
| `map`, `chan`, `func` | 8 | 8 |

A struct's fields are laid out in declaration order, each at the next offset
satisfying its alignment. The struct's alignment is the maximum of its fields'.
The struct's size is rounded up to its alignment. **No field reordering**, which
the specification does not require but every program that uses `unsafe.Offsetof`
or an assembly file assumes.

One rule is easy to miss and the runtime depends on it: a struct that ends in a
zero-size field gets a padding byte, so that taking the address of that field
cannot produce a pointer past the end of the allocation. Otherwise such a
pointer could be attributed to the next object in the heap.

The condition on the padding is narrow, and `ir.Layout` carries it in the
narrow form: the byte is added only when the fields before the zero-size one
occupy at least one byte. A struct whose fields are *all* zero-size is itself
zero-size, so `struct{A, B struct{}}` is 0 bytes and `struct{A int8; B
struct{}}` is 2.

`PtrBytes` in a type descriptor is the offset of the last pointer-containing word
plus one word, not the size. A type whose pointers are all in its first half has
a `PtrBytes` of half its size, and the collector scans only that far.

## Calling convention

Go's internal ABI passes arguments and results in registers, falling back to the
stack when the registers are exhausted.

### `arm64`

| Registers | Use |
| --- | --- |
| R0 – R15 | integer arguments and results |
| F0 – F15 | floating-point arguments and results |
| R16, R17 | the linker's trampoline scratch; never allocated |
| R18 | **reserved by the operating system**; never allocated |
| R19 – R24 | no ABI role, and allocatable |
| R25 | no ABI role; the third materialisation register, never allocated |
| R26 | closure context pointer at a call |
| R27 | the assembler's scratch for an expanded instruction; never allocated |
| R28 | current goroutine |
| R29 | frame pointer |
| R30 | link register; the convention lets a non-leaf body use it as scratch, and nanogo never allocates it |
| F16 – F31 | no ABI role, and allocatable except F30 and F31 |
| RSP | stack pointer, 16-byte aligned always |

Which registers the allocator may choose from is this table read the other way,
and [042](042-arm64-backend.md) states it in that form. Three entries carry a
second role: [026](026-register-allocation.md) reloads a spilled integer value
through R16, R17 and R25, and it takes F30 and F31 for the same purpose because
this convention gives no role to any register above F15.

R16 and R17 cost nothing, because the linker already reserves them. R25 costs
one register out of the allocatable set, and it is the only register this
convention loses to the allocator's needs. It is taken from the top of the
range with no ABI role, so no argument, no result and no runtime register
moves.

### Assignment

Arguments are assigned by walking the parameter list and, within each parameter,
walking its type recursively:

1. A value of scalar type takes the next register of its class.
2. A struct or array is decomposed into its fields; each field is assigned
   independently. A struct whose fields all fit takes several registers.
3. If any part of a value does not fit, the **whole value** goes to the stack.
   Assignment is all-or-nothing per top-level argument.
4. Results are assigned by the same walk over the result list, restarting the
   register counters.

### What the result list is by the time this pass runs

The walk over the result list is a walk over the values the return passes and
the values the call site reads, not over the declared results. Decomposition
runs first ([025](025-lowering-and-rules.md)), so a result wider than a
register has become one value per machine word on both sides: the return passes
one operand per word, and the call site reads one `SelectN` per word, indexed
by the word it starts at rather than by the result it belongs to.

Decomposition stops at `MaxDecomposeParts`, so a result wider than that reaches
this pass whole on both sides, and this pass finishes the split on both.
`splitOperands` turns the return's one operand into one load per word.
`rewriteCallResults` turns the call site's one `SelectN` into one `SelectN` per
word and writes each word into the place the whole value was written to. The
two are the same walk over the same words, which is what makes the caller and
the callee read the same registers.

```
	caller                              callee

	v1 = SelectN <five> [0] call        v9 = Load <five> ...
	v2 = LocalAddr <*five> {f}          MakeResult v9 mem
	v3 = Store [40] v2 v1 mem
	          |                                   |
	          | rewriteCallResults                | splitOperands
	          v                                   v
	SelectN [0..4] call, one per word   Load, one per word
	Store [8], one per word             MakeResult w0 w1 w2 w3 w4 mem
```

The index of a `SelectN` is the word of the result area it reads, so splitting
one result moves every result after it. A five-field struct followed by a slice
puts the slice at word 5 rather than word 1. The pass therefore takes a call's
whole result list or none of it, and the list has to be complete for the reason
the numbering in `ssa/decompose.go` needs it complete: the word a result starts
at is the sum of the widths of the results before it.

Assignment is all-or-nothing per entry of the list it is given, so a list of
words and a list of composite results agree only while the register set holds
them both. The pass places a call's results over the composite list, which is
the list `gc` places, and splits only what that list puts in registers. Where
every result is in registers the two lists give the same registers in the same
order, because they assign the same words in the same order. Where one is not,
they part, and the pass refuses the function rather than emit a call whose two
sides read different registers. The refusal names the function and the
position, which is what the crash it replaced did not.

### The argument area has two parts

The area is **not** one sequence of every argument in order. It is

| Range | Holds |
| --- | --- |
| `[0, stack)` | the values the registers could not hold, arguments then results, each aligned |
| `[spillBase, args)` | one spill slot per value that travelled in a register, in order |

with `spillBase = roundUp(stack, 8)` and `args` the whole area rounded to a
word. The two parts run on separate counters: a value that took registers
advances the spill counter and not the stack one, and the other way round. A
result that travels in registers gets no slot at all, because a result does not
exist yet when the stack grows.

Read as one sequence, the two rules agree with `gc` when every value takes a
register and when none does, and disagree by the size of the stack part
whenever one call mixes them. That is a call whose stack arguments are read
from the wrong words, and nothing reports it. `gc`'s `assignState` in
`cmd/compile/internal/abi` keeps `stackOffset` and `spillOffset` apart for this
reason.

### The area is the callee's signature, not the call site's reads

The size of a call's outgoing area is a function of the callee's signature and
of nothing else. The callee writes a result the registers cannot hold into the
area before it returns, whether or not the call site reads it, so

```go
f1()          // a statement
x := f1()     // an assignment
```

need the same area from the caller.

nanogo read the call's result types off the `OpSelectN` values that named them,
which is what the call site reads. A discarded result names none, so the area
was zero, and `f0` calling `f1() [3000]byte` for its stack depth alone got a
16-byte frame where `gc` gives 3024. `f1` then wrote three thousand bytes over
its caller's frame and everything above it.

A call value's `Type` is memory, so the signature is not recoverable from it.
`ssa.Value.Sig` carries it, set at construction from the function being called,
which holds the signature as its own type in all three forms: a declared
function, a closure, and the method a selection on an interface names.

### Spill space

Even when arguments arrive in registers, the frame reserves space for them. The
reason is `morestack`: growing the stack must be able to save the argument
registers somewhere, and the spill part of the argument area is that somewhere.

This is also why the arguments stack map ([027](027-liveness-and-stackmaps.md))
describes the argument area even for a function whose arguments came in
registers.

### The bound of [025](025-lowering-and-rules.md) is not a bound here

`MaxDecomposeParts` stops decomposition at four parts, on the grounds that an
aggregate larger than that is passed through memory by every calling
convention. That is true of the C conventions and **false of Go's internal
ABI**: `gc` passes a five-field struct of integers in five registers and
returns a nine-field one in nine.

The bound is a code-quality choice inside a function, where a value that is
never passed anywhere may as well stay in the frame. At a call boundary it is
not a choice, so the assignment pass splits whatever the convention says
travels in registers, however many parts that is, and it runs after
decomposition so that it only ever finishes work that stopped at the bound. It
does so on all four sides of a boundary: an incoming parameter in
`rewriteArgs`, a call's operands and a return's values in `splitOperands`, and
a call's results in `rewriteCallResults`.

Raising the bound is not the fix and no value of it is. A bound of eight moves
the same failure to a nine-field struct, because the failure is a value that
crosses a boundary in more registers than decomposition split it into, and
every finite bound leaves a wider value. Raising it also costs inside every
function that only copies such a value, where the parts are live at once and
the allocator spills them back into the frame they came out of. The bound
therefore stays at four and the split happens here.

### No callee-saved registers

Stated in [026](026-register-allocation.md) and repeated here because it is an
ABI property: every register is clobbered by every call.

## ABI0

The older, stack-only convention. All arguments and results on the stack, in the
outgoing argument area, at offsets computed by the same alignment rules.

It has not been retired because hand-written assembly uses it. `cmd/asm`
refuses the `<ABIInternal>` marker outside the runtime, so every assembly
definition in an ordinary package is ABI0, and a Go call to it under this spec
names an ABIInternal symbol that nothing defines. `gc` closes the gap by
**generating a wrapper** per body-less declaration: a function whose own ABI is
ABI0 that calls the ABIInternal definition, or the reverse
(`cmd/compile/internal/ssagen`, `makeABIWrapper`).

**The rule is not built.** It is that nanogo records ABI0 for anything declared
without a body and defined in assembly, driven by the `-symabis` file the go
command writes. What the code does instead: every text symbol `ssagen` writes
is ABIInternal, and the one ABI0 reference it emits is
`runtime.morestack_noctxt`, which is ABI0 because `rtsym` marks that symbol as
assembly and for no other reason.

The two agree today because `driver.checkAssembly` refuses a package with
assembly in it, so the case never arises. Lifting that refusal needs three
things and this spec owns the first: the wrapper, whose body is the generated
function of [The generated functions](#the-generated-functions) with a
different ABI on the symbol; the `-symabis` reader that says which declarations
the assembly defines; and the `-asmhdr` writer of [050](050-driver.md).

## The generated functions

Some functions in an object are not in any source file. The compiler generates
them, and this spec owns the ones whose reason is a calling convention.

They are built as IR and compiled through the ordinary pipeline, which is what
`gc` does as well: a generated function that took a shorter path would be a
second code generator, and the first bug it hit would be one the pipeline
already handles. `ssagen` builds them; `driver` compiles them into the object
beside the package's own functions.

| Function | Why | Built |
| --- | --- | --- |
| the method wrapper `p.(*T).M` | a descriptor's `Ifn` takes a one-word receiver and a value receiver method does not | yes |
| the equality function `type:.eq.<link string>` | a descriptor's `Equal` has no runtime function for this type | yes |
| the hash function `type:.hash.<link string>` | the same decision, made for `Hasher` | yes |
| the ABI0 wrapper | an assembly definition is ABI0 and a Go call is ABIInternal | no |

The first three are [032](032-type-descriptors-and-itabs.md)'s, which gives
their shapes and what `rtype` has to spell to name them. The fourth is this
spec's and is the one that is not built. Its body is one call, which is less
than any of the other three; what it needs and they do not is a text symbol
whose **own** ABI is ABI0, so the arguments arrive in the outgoing argument
area rather than in the registers this spec assigns, and `ssa.AssignABI` has
one answer today.

Every generated function carries `ir.Func.Wrapper`, so its `funcID` is
`abi.FuncIDWrapper`. `runtime.gorecover` counts the frames between itself and
`runtime.gopanic` and skips every frame with that identifier, so a `recover`
below a generated frame keeps working. `gc` emits a tail call and leaves no
frame at all; nanogo has no tail call, so the frame exists and the mark is what
stands in for its absence.

## Frame layout

Given in [027](027-liveness-and-stackmaps.md). The property this spec adds is
that the frame size is fixed before the prologue is emitted, because the prologue
compares the stack pointer against the goroutine's stack guard using it
([035](035-goroutines-and-stack-growth.md)).

## Where the address of a value in memory comes from

A value the register set cannot hold travels in an argument area, and the code
that reads or writes it needs an address. Three cases, and only one of them has
a name in the graph already.

| Case | The name | The copy |
| --- | --- | --- |
| a parameter | its own object, whose storage becomes the incoming area | none: the callee loads from where the caller wrote |
| a call argument | an object the pass makes for the slot of the outgoing area | a block move ahead of the call |
| a result | an object the pass makes for the slot of the result area | a block move ahead of the return |
| a call's result | nothing: the caller's half of a result the registers cannot hold is not built | refused |

[021](021-ssa-construction.md) gives every aggregate parameter a frame slot and
an `OpLocalAddr` for it, and the entry block copies the incoming value into
that slot. When the convention puts the parameter in the area, the assignment
pass makes the area *be* that slot: the copy writes the value over itself and
goes, and the address already in the graph names the incoming words. This is
what `gc` does with such a parameter and it is the case with no copy at all.

Nothing names a slot of an outgoing area or of the result area, so the pass
makes an `*ir.Object` for it. Such an object is **not** in `Func.Frame`: the
frame layout would give it a second slot in the locals and the locals bitmap
would describe it twice. It is not a local. The words belong to a callee's
incoming argument area, and the callee's own bitmap describes them.

A call whose operand was copied into the area no longer carries it as an
operand, and a value split into one operand per register no longer carries it
as one either, so the operand list stops describing what the call passes. The
placement of every call the pass rewrites is therefore recorded rather than
recomputed: a walk of what is left would place every value after it at the
wrong offset and would size the area too small.

### The result area holds no pointer the collector may follow

The arguments bitmap covers the result area in width and marks nothing in it.
At every safepoint of the callee the result has not been written yet, because
the copy that fills it is the last thing before the return, so the words hold
whatever the previous frame left. Describing them by the result's type would
make the collector follow that. `gc`'s bitmap for such a function is the same
all-zero map over the same width.

## The bounds that are left

Decomposition runs before this pass and erases which operands of a call
belonged to one parameter, and [021](021-ssa-construction.md) does not put a
callee's signature on a call. A call's operands are therefore placed one value
at a time. That agrees with the per-parameter walk except when the register set
runs out in the middle of one parameter's parts, which needs a call with
fifteen or more scalar words of arguments followed by an aggregate. The fix is
a call operation that carries its callee's signature.

A second bound is the caller's half of a result the sixteen result registers
cannot hold. The callee writes such a result into its own incoming argument
area, after the arguments the registers could not hold, and `rewriteResults`
does that. Reading it back needs the offset of the result area of *that call*,
which is where the call's stack arguments ended, and the two placement calls a
call site makes, `ABIArgs` then `ABIResults`, do not share the stack counter
that would give it. Until they do, `rewriteCallResults` refuses such a function
by name and by position rather than leave a store no rule lowers. Reaching it
needs a call that returns more than sixteen machine words, which 4 of the 3,076
functions of the sampled corpus do: `net.goLookupIP` and its neighbours call a
function that returns a `dnsmessage.Name`, a 260-byte struct. None of the four
compiled before either, because the store of such a result is a store no rule
lowers.

A third is a result wider than a register that the call site does not write to
one place, which is the forwarding return `return g()` and the forwarding call
`h(g())`. The words come back in registers and the pass has no destination to
write them to, so the same refusal covers it, and it is the other 2 of the 6.
Splicing the words into the reader's operand list would close it, and that
reader is a `MakeResult` or another call, both of which this pass already
rewrites.

## Testing

- Layout: for every type in a corpus, compare `unsafe.Sizeof`, `Alignof`, and
  `Offsetof` computed by nanogo against the same expressions compiled by `gc`.
  This is exhaustive and cheap and it catches the whole class. `ir` does it
  through `reflect` and `unsafe` in the test process, which is `gc`'s answer for
  the same type, and separately against `types2`'s sizes for a corpus of named
  types.
- Calling convention: `ssagen` compiles a function with nanogo, links it against
  a `main` package compiled by `gc`, and runs the result. The caller declares
  the callee without a body and names its ABI in a `symabis` file, so the call
  crosses the boundary for real. That is 18 cases today, not the generated
  corpus of every combination this spec asks for. What covers the combinations
  instead is the distribution corpus, which walks the assignment over every
  function that reaches SSA and refused none of them.
- `PtrBytes` against the reflect package's view of the same type.

The **reverse** direction, nanogo calling a `gc`-compiled function, is covered
by the same tests: the function under test calls helpers `gc` compiled.

## What was wrong

**The spec stated the zero-size padding rule without its condition.** As
written it padded any struct whose last field is zero-size, and `ir.Layout`
once did that, which gave `struct{A struct{}}` and `struct{A, B struct{}}` a
size of 1 where `unsafe.Sizeof` gives 0. It was found by the layout test that
compares against `reflect`.

**The spec stated the ABI0 recording rule as though it were built.** It is
not, and one hard-coded symbol stands in for it. It was found by looking for
the rule in the code and finding the symbol instead.

**The spec said the linker generates the ABI0 wrapper.** It does not. `gc`
generates it, as a Go function it then compiles, and the linker only resolves
the reference. The sentence made the gap look like somebody else's, which is
why the section that names it as this spec's work came after the sentence was
corrected.

**The area was sized from what the call site read.** `abiCallResultTypes` took
the call's result types from the `OpSelectN` values that named them. A result
nothing reads names none, so a statement call to a function returning a value
the registers cannot hold got an area of zero and the callee wrote over its
caller. Go's own `test/stack.go` is where it surfaced: `f0` calls `f1`, which
returns `[3000]byte` and is called for its stack depth alone, and the corrupted
frame turned the next panic into "traceback did not unwind completely". The
section above states the rule the code now follows.
