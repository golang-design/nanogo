# ABI

Every rule here is `gc`'s rule, by [000](000-decisions.md) decision 10. Nothing
in this spec is a design; it is a transcription with the consequences drawn out.
A deviation is not a different choice, it is a bug that corrupts memory.

Type layout is `ir.Layout`. The calling convention is the assignment walk in
`ssa/abi.go` and the pass that rewrites a function to realise it. Both are
built. Over 536 packages of the distribution the assignment **walk** refused 0
of the 20,916 functions that reach SSA construction, and it still does. What
the **pass** refuses was 3 of those 20,916 and none of the 3,711 of the sampled
corpus, measured before either walk moved from the values a boundary carries to
the declared list; those moves closed one shape and opened another and the
distribution has not been swept since. The section below names every shape the
pass refuses and the bounds that are not refusals. ABI0 recording is the one
part of this spec with no code, and the section below says what it would take.

## Type layout

Sizes and alignments follow the specification and the reference implementation:

| Type | Size | Alignment |
| --- | --- | --- |
| `bool`, `int8`, `uint8` | 1 | 1 |
| `int16`, `uint16` | 2 | 2 |
| `int32`, `uint32`, `float32`, `rune` | 4 | 4 |
| `int64`, `uint64`, `float64`, `int`, `uint`, `uintptr`, pointer | 8 | 8 |
| `complex64` | 8 | 4 |
| `complex128` | 16 | 8 |
| `string` | 16 | 8 |
| slice | 24 | 8 |
| interface, `any` | 16 | 8 |
| `map`, `chan`, `func` | 8 | 8 |

A struct's fields are laid out in declaration order, each at the next offset
satisfying its alignment. The struct's alignment is the maximum of its fields'.
The struct's size is rounded up to its alignment. **No field reordering**, which
the specification does not require but every program that uses `unsafe.Offsetof`
or an assembly file assumes.

One rule is easy to miss and the runtime depends on it: a struct that ends in a
zero-size field gets a padding byte, so that taking the address of that field
cannot produce a pointer past the end of the allocation. Otherwise such a
pointer could be attributed to the next object in the heap.

The condition on the padding is narrow, and `ir.Layout` carries it in the
narrow form: the byte is added only when the fields before the zero-size one
occupy at least one byte. A struct whose fields are *all* zero-size is itself
zero-size, so `struct{A, B struct{}}` is 0 bytes and `struct{A int8; B
struct{}}` is 2.

`PtrBytes` in a type descriptor is the offset of the last pointer-containing word
plus one word, not the size. A type whose pointers are all in its first half has
a `PtrBytes` of half its size, and the collector scans only that far.

## Calling convention

Go's internal ABI passes arguments and results in registers, falling back to the
stack when the registers are exhausted.

### `arm64`

| Registers | Use |
| --- | --- |
| R0 – R15 | integer arguments and results |
| F0 – F15 | floating-point arguments and results |
| R16, R17 | the linker's trampoline scratch; never allocated |
| R18 | **reserved by the operating system**; never allocated |
| R19 – R24 | no ABI role, and allocatable |
| R25 | no ABI role; the third materialisation register, never allocated |
| R26 | closure context pointer at a call |
| R27 | the assembler's scratch for an expanded instruction; never allocated |
| R28 | current goroutine |
| R29 | frame pointer |
| R30 | link register; the convention lets a non-leaf body use it as scratch, and nanogo never allocates it |
| F16 – F31 | no ABI role, and allocatable except F30 and F31 |
| RSP | stack pointer, 16-byte aligned always |

Which registers the allocator may choose from is this table read the other way,
and [042](042-arm64-backend.md) states it in that form. Three entries carry a
second role: [026](026-register-allocation.md) reloads a spilled integer value
through R16, R17 and R25, and it takes F30 and F31 for the same purpose because
this convention gives no role to any register above F15.

R16 and R17 cost nothing, because the linker already reserves them. R25 costs
one register out of the allocatable set, and it is the only register this
convention loses to the allocator's needs. It is taken from the top of the
range with no ABI role, so no argument, no result and no runtime register
moves.

### Assignment

Arguments are assigned by walking the parameter list and, within each parameter,
walking its type recursively:

1. A value of scalar type takes the next register of its class.
2. A struct or array is decomposed into its fields; each field is assigned
   independently. A struct whose fields all fit takes several registers.
3. If any part of a value does not fit, the **whole value** goes to the stack.
   Assignment is all-or-nothing per top-level argument.
4. Results are assigned by the same walk over the result list, restarting the
   register counters.

### The result list is the declared one, and the operands are its words

The walk over the result list is a walk over the **declared** results. It is
not a walk over the values a return passes or the values a call site reads, and
the difference is the rule of the section above: assignment is all-or-nothing
per entry of the list it is given, so a list of words and a list of declared
results agree only while the register set holds them both.

Decomposition runs first ([025](025-lowering-and-rules.md)), so a result wider
than a register has become one value per machine word on both sides: the return
passes one operand per word, and the call site reads one `SelectN` per word,
indexed by the word it starts at rather than by the result it belongs to. Those
words are what the pass places *into* the answer the declared walk gives, and
`abiResultSpans` is the map from one list to the other. It reads back the rule
`ssa/decompose.go` states: a result decomposition split is one value per part,
a result it left whole is one value whatever its type is, and the two are told
apart by the value's own type, because every part of a split value is a scalar
or a pointer and only a whole aggregate is multiword. The map has to consume
the value list exactly, or a later result would be placed over words that hold
an earlier one, and a map that does not is refused.

`(Collected, error)` is where the two lists part. `Collected` is fifteen words
and `error` is two, so `gc` gives the struct the first fifteen result
registers, leaves the sixteenth unused and puts the whole `error` in the result
area. A walk of the values the return passes puts the itab of the `error` in
the sixteenth register and only its data word in the area, so both halves end
up somewhere the caller does not read. Inside a nanogo-only program the wrong
rule is self-consistent and prints right answers, and only a comparison against
`gc` reports it.

Decomposition stops at `MaxDecomposeParts`, so a result wider than that reaches
this pass whole on both sides, and this pass finishes the split on both.
`rewriteResults` turns the return's one operand into one load per word.
`rewriteCallResults` turns the call site's one `SelectN` into one `SelectN` per
word and writes each word into the place the whole value was written to. The
two are the same walk over the same words, which is what makes the caller and
the callee read the same registers.

```
	caller                              callee

	v1 = SelectN <five> [0] call        v9 = Load <five> ...
	v2 = LocalAddr <*five> {f}          MakeResult v9 mem
	v3 = Store [40] v2 v1 mem
	          |                                   |
	          | rewriteCallResults                | rewriteResults
	          v                                   v
	SelectN [0..4] call, one per word   Load, one per word
	Store [8], one per word             MakeResult w0 w1 w2 w3 w4 mem
```

The index of a `SelectN` is the word of the result area it reads, so splitting
one result moves every result after it. A five-field struct followed by a slice
puts the slice at word 5 rather than word 1. The pass therefore takes a call's
whole result list or none of it, and the list has to be complete for the reason
the numbering in `ssa/decompose.go` needs it complete: the word a result starts
at is the sum of the widths of the results before it.

A call's results are placed the same way and from the same list. The callee's
signature is on the call (`ssa.Value.Sig`), so the call site walks the declared
results too and maps them onto the `SelectN` values with the same span walk.
Where every result is in registers the two lists give the same registers in the
same order, because they assign the same words in the same order. Where one is
not, they part, and a call site that walked the words would read half of a
result out of a register the callee never wrote.

### The argument list is the declared one too

The same rule and the same reason. A call's operands are the machine words
decomposition left of its arguments, and assignment is all-or-nothing per entry
of the list it walks, so the two lists give the same registers in the same
order only while the register set holds them both. Fifteen integers followed by
a two-word struct is where they part: `gc` leaves the sixteenth integer
register unused and puts the whole struct in the area, and a walk of the words
puts the struct's first word in that register and only its second in the area.
That is a caller writing one half of an argument where the callee reads
neither, and, like the result case, it prints right answers inside a
nanogo-only program.

The list is not `Sig.Params` alone. A method's receiver is not in it, so the
operands of a call to a method of a concrete type are the receiver and then the
words of the parameters, and the operands of a call to a method of an interface
are the receiver's data word and then the same. `abiCallArgTypes` therefore
tries two lists, the parameters alone and one leading operand followed by the
parameters, and takes whichever of the two the span walk of `abiResultSpans`
consumes exactly. Neither, or both, is not an answer, and the walk of the
operand list is taken there.

There is **no rule that an argument in the area puts the arguments after it
there too**. That is the C conventions' rule and Go's internal ABI does not
have it: `gc`'s `assignParamOrReturn` tries `regassignIntegral` for every
parameter independently and falls to `stackAllocate` only for the one that does
not fit. `go tool compile -S` shows it on one line, where a two-word struct
takes the last two integer registers, the `int` after it goes to the area
because the file is exhausted, and the `float64` after *that* is still in F0
because the two files are counted apart.

### The parameter that keeps the caller's words

A parameter the registers cannot hold is already in memory, so
[021](021-ssa-construction.md)'s copy into a frame slot writes it over itself
once the slot is that memory. Decomposition decides only how many stores the
copy is: one where it left the parameter whole, one per word where it split it.
Both are deleted and the object leaves `Func.Frame`, and the address the graph
already had names the incoming words.

Leaving the split form in place is not a slower program, it is a wrong one. The
loads that fill the second slot are the first thing the function does, and the
allocator gives them the registers nothing in the graph says are taken. The
registers the caller left the *following* arguments in are exactly those: an
`OpArg` is live from the caller's store and the allocator's range for it begins
at the value's own definition. A method with a wide value receiver is the
smallest case, and Go's own `test/method5.go` is where it prints the receiver's
words in place of the arguments.

### The placement is recorded, not recomputed

Neither the operands of a call nor the values of a return describe what the
boundary passes once the pass has rewritten them. A copied value is not in the
list at all, a value split into one operand per register has a spill slot the
parts do not add up to, and the words of a result are placed by a walk over a
list they are not in. The placement of every boundary the pass touches is
therefore recorded on `ABI.Calls`, indexed by the value's own identifier, and
every reader takes the record: `ABICallArgs` for a call's operands, `ABIReturn`
for a return's, and `ABICall.Results` for what a call site reads. The register
allocator and the code generator read the same record, so a boundary has one
placement rather than two that have to agree. A walk of the list is the
fallback and is right only where there is no record, which is a boundary
selection created after this pass ran and a function assembled by hand.

### The argument area has two parts

The area is **not** one sequence of every argument in order. It is

| Range | Holds |
| --- | --- |
| `[0, stack)` | the values the registers could not hold, arguments then results, each aligned |
| `[spillBase, args)` | one spill slot per value that travelled in a register, in order |

with `spillBase = roundUp(stack, 8)` and `args` the whole area rounded to a
word. The two parts run on separate counters: a value that took registers
advances the spill counter and not the stack one, and the other way round. A
result that travels in registers gets no slot at all, because a result does not
exist yet when the stack grows.

Read as one sequence, the two rules agree with `gc` when every value takes a
register and when none does, and disagree by the size of the stack part
whenever one call mixes them. That is a call whose stack arguments are read
from the wrong words, and nothing reports it. `gc`'s `assignState` in
`cmd/compile/internal/abi` keeps `stackOffset` and `spillOffset` apart for this
reason.

### The area is the callee's signature, not the call site's reads

The size of a call's outgoing area is a function of the callee's signature and
of nothing else. The callee writes a result the registers cannot hold into the
area before it returns, whether or not the call site reads it, so

```go
f1()          // a statement
x := f1()     // an assignment
```

need the same area from the caller.

nanogo read the call's result types off the `OpSelectN` values that named them,
which is what the call site reads. A discarded result names none, so the area
was zero, and `f0` calling `f1() [3000]byte` for its stack depth alone got a
16-byte frame where `gc` gives 3024. `f1` then wrote three thousand bytes over
its caller's frame and everything above it.

A call value's `Type` is memory, so the signature is not recoverable from it.
`ssa.Value.Sig` carries it, set at construction from the function being called,
which holds the signature as its own type in all three forms: a declared
function, a closure, and the method a selection on an interface names.

### Spill space

Even when arguments arrive in registers, the frame reserves space for them. The
spill part of the argument area is a **home in the caller's frame for the
callee's register-assigned parameters**, and the callee writes it whenever one
of them is live across a call the callee makes.
`abi.ABIParamResultInfo.SpillAreaOffset` is where it starts and `morestack` is
one writer of it, not the only one.

This is also why the arguments stack map ([027](027-liveness-and-stackmaps.md))
describes the argument area even for a function whose arguments came in
registers.

### The outgoing argument area is the callee's for the whole of a call

It follows from the paragraph above and it is the rule the layout has to keep:
**no value may be live in the outgoing argument area across a call, and its
address may not be an operand of one.** The area is not scratch that the callee
reads and returns. It is storage the callee may write at any point between its
entry and its return.

`runtime.typedmemmove` is the shortest demonstration. Its three parameters are
register-assigned, and when `runtime.writeBarrier.enabled` is set it spills all
three into the caller's area at offsets 0, 8 and 16 before calling
`runtime.bulkBarrierPreWrite`. A call whose source argument points into that
area therefore has its own arguments copied over the first three words of the
value it was told to move. [060](060-selfhost.md) records that as the fault
that held stage 2, and `ssa/abi.go`'s `stageArea` is what keeps the rule: a
move that [034](034-write-barriers.md) will give a barrier reads a frame slot,
and a copy out of the area fills that slot first.

The copy that fills it may read the area. Its destination is a frame slot, so
it gets no barrier and lowers to `runtime.memmove`, which is `NOSPLIT|NOFRAME`
hand-written assembly with no spill home to write.

### The bound of [025](025-lowering-and-rules.md) is not a bound here

`MaxDecomposeParts` stops decomposition at four parts, on the grounds that an
aggregate larger than that is passed through memory by every calling
convention. That is true of the C conventions and **false of Go's internal
ABI**: `gc` passes a five-field struct of integers in five registers and
returns a nine-field one in nine.

The bound is a code-quality choice inside a function, where a value that is
never passed anywhere may as well stay in the frame. At a call boundary it is
not a choice, so the assignment pass splits whatever the convention says
travels in registers, however many parts that is, and it runs after
decomposition so that it only ever finishes work that stopped at the bound. It
does so on all four sides of a boundary: an incoming parameter in
`rewriteArgs`, a call's operands and a return's values in `splitOperands`, and
a call's results in `rewriteCallResults`.

Raising the bound is not the fix and no value of it is. A bound of eight moves
the same failure to a nine-field struct, because the failure is a value that
crosses a boundary in more registers than decomposition split it into, and
every finite bound leaves a wider value. Raising it also costs inside every
function that only copies such a value, where the parts are live at once and
the allocator spills them back into the frame they came out of. The bound
therefore stays at four and the split happens here.

### No callee-saved registers

Stated in [026](026-register-allocation.md) and repeated here because it is an
ABI property: every register is clobbered by every call.

## ABI0

The older, stack-only convention. All arguments and results on the stack, in the
outgoing argument area, at offsets computed by the same alignment rules.

It has not been retired because hand-written assembly uses it. `cmd/asm`
refuses the `<ABIInternal>` marker outside the runtime, so every assembly
definition in an ordinary package is ABI0, and a Go call to it under this spec
names an ABIInternal symbol that nothing defines. `gc` closes the gap by
**generating a wrapper** per body-less declaration: a function whose own ABI is
ABI0 that calls the ABIInternal definition, or the reverse
(`cmd/compile/internal/ssagen`, `makeABIWrapper`).

**The rule is not built.** It is that nanogo records ABI0 for anything declared
without a body and defined in assembly, driven by the `-symabis` file the go
command writes. What the code does instead: every text symbol `ssagen` writes
is ABIInternal, and the one ABI0 reference it emits is
`runtime.morestack_noctxt`, which is ABI0 because `rtsym` marks that symbol as
assembly and for no other reason.

The two agree today because `driver.checkAssembly` refuses a package with
assembly in it, so the case never arises. Lifting that refusal needs three
things and this spec owns the first: the wrapper, whose body is the generated
function of [The generated functions](#the-generated-functions) with a
different ABI on the symbol; the `-symabis` reader that says which declarations
the assembly defines; and the `-asmhdr` writer of [050](050-driver.md).

## The generated functions

Some functions in an object are not in any source file. The compiler generates
them, and this spec owns the ones whose reason is a calling convention.

They are built as IR and compiled through the ordinary pipeline, which is what
`gc` does as well: a generated function that took a shorter path would be a
second code generator, and the first bug it hit would be one the pipeline
already handles. `ssagen` builds them; `driver` compiles them into the object
beside the package's own functions.

| Function | Why | Built |
| --- | --- | --- |
| the method wrapper `p.(*T).M` | a descriptor's `Ifn` takes a one-word receiver and a value receiver method does not | yes |
| the equality function `type:.eq.<link string>` | a descriptor's `Equal` has no runtime function for this type | yes |
| the hash function `type:.hash.<link string>` | the same decision, made for `Hasher` | yes |
| the ABI0 wrapper | an assembly definition is ABI0 and a Go call is ABIInternal | no |

The first three are [032](032-type-descriptors-and-itabs.md)'s, which gives
their shapes and what `rtype` has to spell to name them. The fourth is this
spec's and is the one that is not built. Its body is one call, which is less
than any of the other three; what it needs and they do not is a text symbol
whose **own** ABI is ABI0, so the arguments arrive in the outgoing argument
area rather than in the registers this spec assigns, and `ssa.AssignABI` has
one answer today.

Every generated function carries `ir.Func.Wrapper`, so its `funcID` is
`abi.FuncIDWrapper`. `runtime.gorecover` counts the frames between itself and
`runtime.gopanic` and skips every frame with that identifier, so a `recover`
below a generated frame keeps working. `gc` emits a tail call and leaves no
frame at all; nanogo has no tail call, so the frame exists and the mark is what
stands in for its absence.

## Frame layout

Given in [027](027-liveness-and-stackmaps.md). The property this spec adds is
that the frame size is fixed before the prologue is emitted, because the prologue
compares the stack pointer against the goroutine's stack guard using it
([035](035-goroutines-and-stack-growth.md)).

## Where the address of a value in memory comes from

A value the register set cannot hold travels in an argument area, and the code
that reads or writes it needs an address. Seven cases, and only one of them has
a name in the graph already.

| Case | The name | The copy |
| --- | --- | --- |
| a parameter | its own object, whose storage becomes the incoming area | none: the callee loads from where the caller wrote |
| a call argument | an object the pass makes for the slot of the outgoing area | a block move ahead of the call |
| a whole result | an object the pass makes for the slot of the result area | a block move ahead of the return |
| a result decomposition split | none: the words are operands of the return | one store per word, which the code generator emits like any other operand the convention put in the area |
| a call's whole result the registers could not hold | an object the pass makes for the slot of the call's result area | a block move out of the area, in place of the store the call site already made |
| a call's result the registers could not hold that decomposition split | an object the pass makes for the slot of the call's result area | one load per word, behind the call |
| a call's result the call site writes nowhere | a frame slot the pass makes, and this one is a local | a store behind the call, and the boundary below loads out of the slot |

A result decomposition already split needs no address on the callee's side at
all. Its words are values of the machine, each is placed on the word of the
area it belongs to, and the code generator stores each one where an argument in
the stack part would go. The block move is for the other shape, a result wide
enough that decomposition left it whole, which reaches the return as one load
out of memory and has no machine form to store. The call site is the mirror:
one load per word where the words are separate values, and one block move where
they are not.

The loads a call site makes go behind the call, for the reason the spill's
store does: the words they read are in the call's outgoing argument area and
the next call this function makes writes over it.

[021](021-ssa-construction.md) gives every aggregate parameter a frame slot and
an `OpLocalAddr` for it, and the entry block copies the incoming value into
that slot. When the convention puts the parameter in the area, the assignment
pass makes the area *be* that slot: the copy writes the value over itself and
goes, and the address already in the graph names the incoming words. This is
what `gc` does with such a parameter and it is the case with no copy at all.

Nothing names a slot of an outgoing area or of the result area, so the pass
makes an `*ir.Object` for it. Such an object is **not** in `Func.Frame`: the
frame layout would give it a second slot in the locals and the locals bitmap
would describe it twice. It is not a local. The words belong to a callee's
incoming argument area, and the callee's own bitmap describes them.

A call whose operand was copied into the area no longer carries it as an
operand, and a value split into one operand per register no longer carries it
as one either, so the operand list stops describing what the call passes. The
placement of every call the pass rewrites is therefore recorded rather than
recomputed: a walk of what is left would place every value after it at the
wrong offset and would size the area too small.

### The forwarded result

`return g()` and `h(g())` hand a call's result straight to another boundary.
Every rewrite above reaches a value at a boundary through the address of the
place it lives in, and a forwarded result lives in no place: the words are in
the registers the callee left them in, or in the call's result area, and
nothing writes them down. So `spillResults` writes them down. It makes a slot,
stores the result into it behind the call, and points the reader at a load out
of it. The store is then the destination the caller's half of the result needs
and the load is the address the boundary below needs, and both are rewrites
this pass already makes.

This slot **is** in `Func.Frame`, and it is the only object this pass makes that
is. It holds a live value across a boundary, so the collector has to find it,
and it finds a local through the locals bitmap of
[027](027-liveness-and-stackmaps.md). The slots above hold a value only for the
instant of a call and the callee's own bitmap describes them.

The store goes directly behind the call and not next to the reader. A result
the registers could not hold is in the call's outgoing argument area, and the
next call this function makes writes over that area, so a copy out of it that
is not ahead of every other call reads what the later call left. The condition
the pass checks says the same thing in the graph: the reader has to read the
memory the call produced. A reader that does not is left alone.

The store into the slot is one call and it is the one call the area may be an
operand of, for the reason the section above gives: it lowers to
`runtime.memmove` and not to `runtime.typedmemmove`, because its destination is
a frame slot.

A result nobody reads needs no slot and gets none, which is the discarded
result of `_, err := g()`. The words come back whatever the call site wants, so
the result after it still starts at the word after the last of them, and the
pass splits it into one `SelectN` per word with nothing behind them. Leaving it
whole is not the cheaper answer: `ssagen` indexes a call's results by the word
each reads and refuses a list with a hole in it.

### A split reads the memory that is live where it goes

The loads a split makes are scheduled at the boundary, and the memory they read
is the memory live there, not the memory the load they replace read. The two
differ as soon as this pass has already put a block move ahead of the same
boundary, which a return of one result the registers hold and one they do not
does: the copy of the second is ahead of the loads of the first. A load placed
there reading the older memory is two memory values live at one point, which is
`InvMemChain` in `ssa/verify.go`, and below the verifier it is a load a later
pass may move across a store. Reading the newer memory moves no read across a
store the program wrote, because every memory this pass inserts at a boundary
writes a slot the pass itself made, and no value of the function names one.

### The result area holds no pointer the collector may follow

The arguments bitmap covers the result area in width and marks nothing in it.
At every safepoint of the callee the result has not been written yet, because
the copy that fills it is the last thing before the return, so the words hold
whatever the previous frame left. Describing them by the result's type would
make the collector follow that. `gc`'s bitmap for such a function is the same
all-zero map over the same width.

## The bounds that are left

Decomposition runs before this pass and erases which operands of a call
belonged to one parameter. The signature's parameter list is read back over
them the way its result list is, and `abiCallArgTypes` is that read. What it
cannot recover is a **receiver decomposition split**: `ir.Converter` keeps a
method's receiver out of `Params`, the way `types2` keeps it out of `Params()`
and in `Recv()`, so a method call passes one operand more than the signature
declares and the receiver's declared type is recovered from that operand. Where
decomposition split the receiver into words there is no such operand, the type
is in no list at all, and the walk of the operand list is taken instead. It is
right wherever no register file runs out inside one argument, which is every
call with fewer than fifteen scalar words of arguments before the aggregate.

A second is a value wider than a register that reaches a call as an operand and
that this pass cannot take the address of, because it did not come out of
memory. There is no address to copy from, so the pass refuses by name rather
than leave an operand the code generator has no move for. It is 2 of the
20,916, and both are a closure:
`internal/trace/testtrace.getOrCreateThread.func1` and the `func1` of
`net/http/httptrace`'s `compose2to0`.

A third is a call result wider than a register whose reader carries no memory,
which is a struct compared against another in a `switch`. The store the spill
would make has nowhere in the chain to go, because the reader that would anchor
it reads no memory. It is the remaining 1 of the 20,916, in
`crypto/mldsa.newPublicKey`. A slot would not compile the function either: what
is left is a comparison of two values wider than a register, and nothing below
this pass splits one.

A fourth is a boundary whose values `abiResultSpans` cannot map onto the
declared results, which is a graph where the values a return passes or a call
site reads are not the words of those results. A map that ended early or ran
past the end would place a later result over words an earlier one holds, so the
pass refuses instead. It replaced no refusal: before the walk read the declared
list there was no map to fail. Nothing in Go's own corpus reaches it, because
the map reads back the rule decomposition follows and decomposition is what
produced the values.

## Testing

- Layout: for every type in a corpus, compare `unsafe.Sizeof`, `Alignof`, and
  `Offsetof` computed by nanogo against the same expressions compiled by `gc`.
  This is exhaustive and cheap and it catches the whole class. `ir` does it
  through `reflect` and `unsafe` in the test process, which is `gc`'s answer for
  the same type, and separately against `types2`'s sizes for a corpus of named
  types.
- Calling convention: `ssagen` compiles a function with nanogo, links it against
  a `main` package compiled by `gc`, and runs the result. The caller declares
  the callee without a body and names its ABI in a `symabis` file, so the call
  crosses the boundary for real. That is 18 cases today, not the generated
  corpus of every combination this spec asks for. What covers the combinations
  instead is the distribution corpus, which walks the assignment over every
  function that reaches SSA and refused none of them.
- A result the registers cannot hold: `internal/e2e` builds three packages and
  gives nanogo the middle one, so `gc` calls into what nanogo compiled and what
  nanogo compiled calls into `gc`, and every line of the output is compared
  against an all-`gc` build of the same three packages. It is the only test
  that can see this rule. A placement over the words a return passes rather
  than over the declared results is self-consistent inside one compiler and
  prints right answers there.
- Arguments the registers cannot hold: the same three packages and the same
  comparison, over the five shapes the argument placement is easy to get wrong.
  A method with a wide value receiver, an aggregate the registers refuse
  followed by scalars, fifteen integers and then a two-word struct, a float
  after an argument in the area, and a variadic call. Each of them is silent
  inside one compiler for the reason the result case is.
- `PtrBytes` against the reflect package's view of the same type.

The **reverse** direction, nanogo calling a `gc`-compiled function, is covered
by the same tests: the function under test calls helpers `gc` compiled.

## What was wrong

**The spec stated the zero-size padding rule without its condition.** As
written it padded any struct whose last field is zero-size, and `ir.Layout`
once did that, which gave `struct{A struct{}}` and `struct{A, B struct{}}` a
size of 1 where `unsafe.Sizeof` gives 0. It was found by the layout test that
compares against `reflect`.

**The spec stated the ABI0 recording rule as though it were built.** It is
not, and one hard-coded symbol stands in for it. It was found by looking for
the rule in the code and finding the symbol instead.

**The spec said the linker generates the ABI0 wrapper.** It does not. `gc`
generates it, as a Go function it then compiles, and the linker only resolves
the reference. The sentence made the gap look like somebody else's, which is
why the section that names it as this spec's work came after the sentence was
corrected.

**The spec said the result walk is a walk over what a return passes.** It said
so under "What the result list is by the time this pass runs", and both sides
of the pass did that. Assignment is all-or-nothing per entry of the list it
walks, so a list of words and a list of declared results part as soon as the
register set runs out inside one result: `(Collected, error)` put the itab of
the `error` in the sixteenth result register and only its data word in the
area, where `gc` puts the whole `error` in the area and leaves the register
unused. It was found by compiling one package against a `gc`-compiled caller
and comparing the output, which is the only thing that can see it. The section
above states the rule the code now follows.

**The loads of a split read the memory the load they replaced read.** A return
of one result the registers hold and one they do not puts the copy of the
second ahead of the loads of the first, so the loads read a memory that was no
longer live and the function no longer satisfied `InvMemChain`. Below the
verifier it is a load a later pass may move across a store. It was found by the
verifier that runs after this pass, on `driver.compileFunc`, and the section
above states the rule the code now follows.

**The spec said the caller's half of a result the registers cannot hold was not
built.** It is: `rewriteCallResults` reads such a result back out of the call's
result area, and it takes the offset from the same stack counter the arguments
left, which is what the sentence said was missing. The row of the table above
that called the case refused was wrong in the same way, and both were found by
reading `readFromArea` while closing the forwarded result beside it.

**The spec said the argument side had no declared list to read.** It said so
under "The bounds that are left", and the walk placed a call's operands one
value at a time. A call of fifteen integers and a two-word struct put the
struct's first word in the sixteenth register and only its second in the area,
where `gc` leaves the register unused and puts the whole struct in the area, so
the callee read one half of the argument out of a register the caller never
wrote and the argument after it out of the wrong word. It was found by
compiling one package against a `gc`-compiled caller and comparing the output.
The section above states the rule the code now follows, and the bound that is
left in its place is a receiver decomposition split.

**The rule was read as the C conventions' rule.** An argument the registers
cannot hold was thought to put every argument after it in the area as well.
Go's internal ABI has no such rule, `gc` assigns each parameter independently,
and building the sticky form would have moved every argument after the first
aggregate in a very large number of functions. It was found by reading `gc`'s
own output for a call that mixes the two.

**A parameter decomposition split kept a second slot in the locals.**
`rewriteArgs` made the incoming argument area the storage of a parameter the
registers cannot hold only where decomposition had left the parameter whole.
Where it had split the parameter the copy was one store per word, none of them
matched, and the entry block kept a load per word to fill a slot the frame did
not need. Those loads take the registers the caller left the arguments after
the parameter in, so a method with a wide value receiver returned the
receiver's two words in place of its two arguments. It was found by Go's own
`test/method5.go` and the section above states the rule the code now follows.

**The area was sized from what the call site read.** `abiCallResultTypes` took
the call's result types from the `OpSelectN` values that named them. A result
nothing reads names none, so a statement call to a function returning a value
the registers cannot hold got an area of zero and the callee wrote over its
caller. Go's own `test/stack.go` is where it surfaced: `f0` calls `f1`, which
returns `[3000]byte` and is called for its stack depth alone, and the corrupted
frame turned the next panic into "traceback did not unwind completely". The
section above states the rule the code now follows.
